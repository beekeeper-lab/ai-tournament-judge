On the uniformity

Four judges independently landing this close is worth a second look, not applause. Two readings are available and the panel report should say which it believes: either the submission genuinely has a consistent character — competent throughout, one step short of demonstrated in every area — or four instances of the same base model reading the same evidence package produce correlated output, and the panel's apparent agreement is less independent than its structure implies. The framework enforces independence structurally through staging, but staging cannot make one model into four people. atj validate reports checks for near-duplicate wording and found none; that is a contamination detector, not a correlation detector.

What the judges converged on

Findings that more than one judge reached independently, with no access to each other's reports.

Strengths, agreed

  • Refusal is implemented, not advertised. All four traced the stated principle — refuse rather than guess — into executed behavior: the CSV adapter refusing to infer a credit sign, the control-total gate rejecting a statement for a genuine $500 discrepancy, the matcher declining to be a global optimizer, and the D1 detector refusing to report a 0% match rate against a feed that was never loaded.
  • The AI boundary is structural. An exhaustive grep across all 22 files of src/fin/ found no network, HTTP or model import or call site. Money and parsing cannot silently become model output, because no model is reachable from them.
  • Privacy controls are enforced in code and were executed. Vault root 0700, archived source 0600, dispute CSV 0600, a card-number guard that raises at config load with tests behind it, and a shipped pre-commit hook that blocks ledger data and Luhn-valid card numbers.

One criterion is already marked evidence_limited_criteria: [reliability], which means the panel will carry an NE and this team will have no finalizable total. That is the correct outcome, not a failure, and it will propagate into the head-to-head.

Why reliability is NE

The submission's reliability story is its end-to-end browser suite. Three executions against the same commit and the same image produced three different outcomes: one reached stage 7 of 11 and stalled; one stopped at stage 3 with a 90-second download timeout while a second container shared the host; one, re-run in isolation specifically to settle that question, ended with a Chromium renderer crash at stage 3 after roughly seven seconds of suite time. None of the three was classified. The submission's own pass claim is internally inconsistent — the README states both "34/34" and "42/42" against 43 check sites. A judge could defend a low score or a high one from this package, which is exactly what NE is for.

This is a statement about the evidence, not a finding against the submission. Nothing observed shows the suite failing for a reason traced to the team's code.

Two environmental limitations were handled differently, on purpose. A missing declared prerequisite — poppler-utils for one team, ffmpeg for the other — is an operator error that penalises a submission for something outside it, so both were fixed by amending the approved image. The sandbox's 64 MB tmpfs is not: it is a framework-wide cap applied identically to everyone, and moving it mid-event for the one team it constrains would be the unfair act. The consequence is recorded rather than removed.

The evidence audit: three rounds

The evidence stage took three full audit passes to clear. Each pass found real errors the previous pass missed.

2FAIL 2 major, 1 minor, 2 advisory Nine ledger requirement rows had been repointed, but the walk stopped at the nine the first audit named. R12's claim that the package makes no network or LLM call cited an observation that greps the skill files and never examines src/fin/ at all.
3PASS WITH ADVISORIES 5 minor, 4 advisory Residual citation and timestamp defects, none changing a conclusion, an evidence class, a confidence rating, or any number a judge scores against.
Three of the errors were introduced by the repairs

Round 2 found that a row written during the round-1 repair asserted playwright 1.56.0 as a high-confidence direct observation. No run record contains that number: the probe that was supposed to measure it raised AttributeError and returned nothing, and the only measured version anywhere in the event is 1.63.0. The value was fabricated, inside a row whose entire purpose was to assure judges the runtime had been measured rather than assumed.

Round 3 found the same class again one line over: the corrected row still attributed starlette 1.6.0 to a measurement that was never taken. It also found that the round-1 repair to Containerfile.ledger cited src/fin/ingest/pdf.py, a path that does not exist at the pinned commit.

Repair is a source of defects, not just a sink. An audit cycle that stops at the first PASS stops one round too early.

The headline finding

The deterministic tooling cannot detect a false claim. It never could, and nothing in the event surfaced that until a model looked.

atj validate reports returned zero findings at every single stage — before audit 1, between every repair round, and after audit 3. It returned zero findings on manifests that contained nine citations pointing at the wrong observation, a scan credited to an observation that never examined the code in question, and a fabricated version number.

The reason is structural, not a bug. validate reports checks that an evidence identifier resolves — that the id exists in the document. It cannot check that the target contains the claim made of it. Both properties look identical to a schema.

The practical consequence for anyone running this framework:

  • A green validate reports is necessary and nowhere near sufficient. It means the artifact is well-formed, not that it is true.
  • The LLM audit is doing load-bearing work. It is not ceremony layered on top of real checks; on this event it was the only thing that caught any of the substantive errors.
  • One audit pass is not enough when the same pass also specifies repairs. Three passes found a decreasing but non-zero number of real defects each time.

This is the most valuable result the live trial has produced, and it is a finding about the framework, which is exactly what the event exists to test.

Why most of these were not fixed during the event

The repository rule is that an active event's rubric, weights, personas, bracket policy and evidence are frozen once judging begins. D1 is the clearest case: giving the judges a Write tool changes the persona definition, which bumps judge-*@1.0.0 to @1.1.0 in framework/personas.md. team-ledger's four judgments already record @1.0.0. If team-podcast's recorded @1.1.0, the two panels would have been produced by different personas and the head-to-head that compares them would be comparing unlike things.

The workaround — the orchestrator persisting each returned document verbatim — is explicitly sanctioned by the skill's own step 4, which permits holding a report in the orchestrator's context rather than in staging.

Remediation plan

Three tiers, ordered by what the live event permits. The source of truth for this plan is docs/framework-fix-plan.md; this section is the review surface.

Tier 1 — land now, during the event

Changes that touch no rubric, no persona, no policy, no evidence, and no number.

  • T1.1 (D2) — add the model block to framework/templates/individual-judgment.md, documenting what schemas/judgment.schema.json already enforces. Add a release-check assertion that every template satisfies its own schema, so this class cannot recur silently.
  • T1.2 (D6) — narrow .claude/hooks/pre-advance.sh so it inspects the command being executed rather than the whole command string including commit-message bodies and heredoc content. The guard stays blunt about actual execution; it stops firing on documentation.

Tier 2 — after live-trial-2026 reaches complete

  • T2.1 (D1) — give the four judge personas a Write tool scoped to workspaces/<event>/staging/<team>/, bump each to @1.1.0 in framework/personas.md, and add an end-to-end test that spawns a persona and asserts it can produce its own artifact. A persona that cannot write the file its skill demands is a contract violation the test suite should catch.
  • T2.2 — extend atj release-check to cross-check every agent definition's declared tools against the artifacts its skill requires it to produce. D1 existed because nothing compared the two.

Tier 3 — next framework version, needs design

T3.1 (D4) — make a misdirected citation structurally detectable. Semantic truth is not checkable, but this specific failure is, through bidirectional linking:

Requirements table              Direct observations table
  R2 → cites ev-ledger-06         ev-ledger-06 → supports [R2, R3, R4, R9]

atj validate reports then asserts the two agree.

A row citing an observation that does not claim to support it becomes a blocking finding. This catches the exact nine-row failure from audit 1 deterministically, because the observation's author has to independently assert the same link — one person's slip no longer passes silently. It requires a schema change and a migration for existing manifests, which is why it is not a mid-event fix.

T3.2 — record in framework/rubrics/README.md that a single audit pass is insufficient when that pass also specifies repairs, and that the repair round must itself be audited. Three rounds on this event; each found defects the last one missed, and three of those defects were created by the repairs.
