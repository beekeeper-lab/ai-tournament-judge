# Consolidated Team Report — team-ledger (Hive Ledger)

## Executive summary

Four independent judges evaluated the same submission at commit `9d21b770` against
the same evidence package (`ev:live-trial-2026:team-ledger:9d21b7707f20:b859a240`)
under `submission-evaluation@1.0.0`. All four returned complete reports with no
`NE` on any criterion, and `atj score` reports every criterion in the aligned
band, no possible outlier, no integrity problem, and no required adjudication.

The panel agrees on the submission's character without needing to be told: a
local-first personal-finance CLI whose governing principle is that the system
refuses rather than guesses, and whose output is the set of charges it cannot
explain. Every judge found that principle implemented rather than asserted, and
every judge located the ceiling in the same place — the last step short of
demonstration. judge-security-ops states it directly: "Consistent quality,
consistent ceiling."

One confirmed defect was named by all four judges independently: two of four
ingest rejection paths surface as a Python traceback instead of the clean
`REJECTED <file>: <reason>` contract (`ev-ledger-05`). One documentation defect
was confirmed by all four: the tier-0 match keys on `external_ref`, not on the
`order_id` the skill text and README name (`ev-ledger-16`, `ev-ledger-06`,
manifest R13).

The panel does not agree on how much weight the unexercised paths deserve, and
does not agree on the severity of the `fin sql` surface. Those splits are
interpretive, not factual, and are reported below rather than averaged. Three
single-judge findings of real consequence — the reclassification no-op
(judge-backend), the dispute as-of clock (judge-product-agentic), and the
zero-exit after a failed post-ingest revalidation (judge-frontend-ux) — were
each raised by one judge only and were neither contradicted nor corroborated by
the other three. They are preserved as minority concerns and carried to the
open-questions section.

The consolidator is a neutral packager, not a fifth judge. No individual score
below was altered, and no finding below originates with the consolidator.

## Per-criterion agreement analysis

Scores and confidences are quoted from `summaries/team-ledger.json`.

### functional — aligned, all four at 4.0

Confidence: high, high, medium (judge-product-agentic), high.

Shared basis: nine of ten advertised subcommands ran to correct completion in
sandboxed records (`ev-ledger-01`, `ev-ledger-02`, `ev-ledger-04`,
`ev-ledger-06`, `ev-ledger-07`), the control-total gate rejected a statement for
a genuine $500 discrepancy (`ev-ledger-08`), the balanced fixture parsed all four
documented layout hazards (`ev-ledger-09`), and re-ingest was idempotent
(`ev-ledger-04`). All four judges read the run records rather than the manifest
summary and all four declined to treat the unexercised PDF CLI seam as a failure.

Where they diverged without diverging on score: each judge named a different
reason the submission is not a 5. judge-backend named the reclassification no-op
and the unreachable tier 3. judge-frontend-ux named the `external_ref`
documentation defect as a silent degradation of the headline path.
judge-product-agentic named the unexecuted dispute state machine as "the single
largest unverified claim in the package" and recorded medium confidence for that
reason. judge-security-ops named the unrun `sniff`/`pdftotext` path and the
untested `AMBIGUOUS` outcome.

### product — aligned, range 1.0, judge-frontend-ux at 3.0 against three at 4.0

Confidence: medium, high (judge-frontend-ux), high, medium.

This is an interpretation split about which surface is the product, not a
dispute about facts. All four judges observed the same artifacts. judge-frontend-ux
judged a CLI by its live interaction surface — help text, empty states, the error
contract, and whether the headline command names its headline result — and found
a traceback on a routine user error, three silent `analyze` empty states, bare
argparse subcommand help, and `fin match` printing `committed=2, unmatched=1`
while naming no unmatched charge. judge-backend, judge-product-agentic and
judge-security-ops weighted problem fit and the quality of the generated reports,
which judge-frontend-ux also rated the best-designed surface in the submission.
The judge scoring lowest recorded the highest confidence.

Every finding in judge-frontend-ux's `product` section is directly observed in a
run record. Two of the three judges scoring 4 named the same traceback defect in
their own `product` section (judge-product-agentic F4, judge-security-ops F4) and
still scored 4. judge-backend classified the silent `analyze recurring` output as
ordinary hardening he did not count against any score, while judge-frontend-ux
counted it as a confirmed defect. That classification difference, not a
difference in observation, is what separates the scores.

### agentic — aligned, range 1.0, judge-backend and judge-frontend-ux at 3.0 against judge-product-agentic and judge-security-ops at 4.0

Confidence: medium for all four.

The panel agrees on three facts. The allocation of work between model and code is
correct and structurally enforced, with no model, HTTP or network call site
anywhere in the 22-file package (`ev-ledger-20`). The skill files carry real
operating constraints rather than persona padding, including refusal rules aimed
at the model's known failure modes (`ev-ledger-18`). Runtime effectiveness is
entirely unobserved, which is an event constraint and not the team's doing.

The split is over what unobserved effectiveness plus factual errors in the
instruction text should cost. judge-backend: "The design deserves a 4; the
execution does not yet," citing two skill statements false against the
implementation. judge-frontend-ux reached the same 3 on the same shape of
argument plus the absence of any eval, transcript or routing check.
judge-product-agentic scored 4 on the reasoning that three of the criterion's
four sub-questions are answerable from artifacts, and stated the counterfactual
himself: "If the panel weights demonstrated agent behavior heavily, this belongs
a point lower, and I would not argue hard against that." judge-security-ops
scored 4 calling the control model "the best thing in this submission" while
recording the same unobserved effectiveness as the reason it is not a 5.

All four considered and rejected `NE`, each giving an explicit reason.

### engineering — aligned, all four at 4.0, range 0.0

Confidence: high, medium (judge-frontend-ux, who read six of twenty-two modules
closely and said so), high, high.

Unanimous on the reasons: module boundaries follow the domain with no layering
inversions, integer cents throughout, content-derived ids that make idempotence a
property rather than a check, atomic tmp-then-replace writes with deterministic

Unanimous on the ceiling as well, though each judge named a different member of

concentrated outside the well-trodden CSV path.

### reliability — aligned, range 1.0, judge-security-ops at 4.0 against three at 3.0

Confidence: high, high, high, medium (judge-security-ops).

All four observed the same suite result (35 passed, exit 0, offline,
`ev-ledger-12`) and all four praised its property-shaped targets. The divergence
is over which untested thing matters most and whether the strong prevention layer
outweighs it.

judge-backend and judge-product-agentic located the gap in `src/fin/dispute.py`:
zero tests, and only the `NO_STATEMENT` branch ever executed, on the module that
computes a legal clock and a dollar figure. judge-backend: "A genuinely
thoughtful 35-test property suite that leaves the money-and-deadline module
entirely uncovered is a 3." judge-frontend-ux reached 3 on a different gap — no
test imports `fin.cli`, so exit codes, the `REJECTED` contract and every rendered
report are uncovered, and the one exit-code contract an automated caller relies
on is wrong on the post-ingest validation path.

judge-security-ops reached 4 by scoring prevention, detection and recovery as
"clearly above event standard and verified by execution" and treating
diagnosability as the single weak leg. He located the material gap in the
untested `AMBIGUOUS` outcome rather than in dispute coverage, and recorded medium
confidence because his three supporting findings are source inferences with no
confirming run.

Note for the panel: judge-security-ops did not address dispute coverage, and
judge-backend and judge-product-agentic did not address the `AMBIGUOUS` gap. The
scores differ partly because the judges examined different holes, not because
they disagreed about any hole either of them examined.

### security — aligned, all four at 4.0, range 0.0

Confidence: high, high, medium (judge-product-agentic), high.

Score alignment here conceals the panel's widest interpretive gap, described
under Material disagreements. All four confirmed the same demonstrated controls:
vault root `0700` and archived raw source `0600` (`ev-ledger-11`), dispute CSV
`0600` (`ev-ledger-07`), the PAN guard raising at config load with two tests
behind it, a shipped `hooks/pre-commit` scanner (`ev-ledger-19`), and no network
or model surface in the deterministic core (`ev-ledger-20`). All four
independently ran their own injection scan and all four found nothing directed at
an evaluator, corroborating `ev-ledger-10`.

All four also agree the permission model is applied more narrowly than the
README's "every output" framing, corroborating the manifest's own scope caveat on
R14 (`ev-ledger-14`).

### innovation — aligned, all four at 4.0, range 0.0

Confidence: medium for all four.

Unanimous: the originality is in the problem framing rather than the machinery,
and it is substantive. D0 replaces statistical fraud detection with a declared
card-to-merchant binding and fires on transaction one. The matcher refuses to be
a global optimizer on the stated grounds that a higher match rate hides fraud.
The dispute model re-tags an expired billing-error window rather than dropping
it. Unanimous on the ceiling: the most ambitious components are the least
demonstrated.

## Confirmed weaknesses

### Confirmed defects

- **PD1 — Inconsistent ingest error contract.** Two of four rejection paths emit
  a full Python traceback instead of `REJECTED <file>: <reason>`. Nothing is
  written either way. `ev-ledger-05`. Named by all four judges
  (judge-backend F4, judge-frontend-ux B2, judge-product-agentic F4,
  judge-security-ops F4). judge-security-ops adds that in a multi-path ingest it
  aborts the loop after earlier files have committed and before `_revalidate`
  runs.
- **PD2 — Tier-0 documentation names the wrong column.** Tier 0 keys on
  `external_ref`; the skill text and README attribute it to `order_id`. A feed
  matching the documented column list silently degrades to tier-1 amount+date
  matching. `ev-ledger-16`, `ev-ledger-06`, manifest R13. Confirmed by all four.
  judge-frontend-ux rates it the highest-value fix in his report: "the only
  defect here that degrades a real user's results rather than their experience."
- **PD3 — `UNMATCHED` links persist `method="AMOUNT_DATE_UNIQUE"`.** Visible in
  user-facing output as `AMOUNT_DATE_UNIQUE | UNMATCHED | 0.0`. `ev-ledger-06`.
  judge-backend F7, judge-product-agentic F5. Both note that other code queries
  that table.
- **PD4 — `src/fin/dispute.py` has no tests and only its `NO_STATEMENT` branch
  ever executed.** Every run shows `statements 0`. `ev-ledger-07` plus the test
  index. judge-backend F3, judge-product-agentic F2. judge-product-agentic
  declines to score it as failure and records it as the largest unverified claim
  in the package.
- **PD5 — Documentation overreach in the invariant layer.** Two distinct
  instances: `validate.py`'s docstring claims a bucket-partition check the code
  does not perform (judge-backend F9), and `store.py` says invariants are
  asserted "after every mutation" while only a successful non-dry-run ingest
  revalidates (judge-security-ops F11). Artifact evidence at the pinned commit.
- **PD6 — `_infer_year` silently assigns an out-of-cycle date.** Observed as
  `2026-12-20` on a statement whose billing period is `2026-07-15 .. 2026-08-14`,
  in the team's own hazard fixture, with no warning. judge-backend F5 only,
  directly observed in `runs/team-ledger-pdf-grammar-01.json` (`ev-ledger-08`).
  He notes the control-total gate checks amounts, not dates.
- **PD7 — Re-ingest does not reclassify.** `.claude/skills/fin-analyze/SKILL.md`
  instructs the agent to re-ingest after editing rules, which judge-backend
  established cannot take effect: known source ids `continue` before the
  transaction is touched, and `_merge` updates neither `category` nor
  `merchant_family`. judge-backend F1 only, established by direct code read and
  corroborated by the `0 new, 0 merged, 1 already known` output in
  `ev-ledger-04`. He rates it his top fix.
- **PD8 — Three of four `analyze` modes have no empty state; `recurring` prints
  nothing at all.** `ev-ledger-07`. judge-frontend-ux B3 scores it as a defect;
  judge-backend F11 records the same observation and explicitly does not count it
  against any score. A classification split on an agreed fact.
- **PD9 — `fin match` names no unmatched charge**, printing only counts, on the
  command implementing the product's stated thesis. judge-frontend-ux B4 only.
  `ev-ledger-06`.
- **PD10 — D1's finding title mislabels card charges as "merchant-feed
  charges".** judge-product-agentic F10 only. Minor, but the skill instructs the
  agent to relay the text.
- **PD11 — `hooks/pre-commit` blocks `*.CSV` but not lowercase `*.csv`.**
  judge-security-ops F14 only, read at `ev-ledger-19`. He notes `.gitignore`
  covers the common case and the hook is the backstop for `git add -f`.
- **PD12 — CLI discoverability cluster.** Bare argparse subcommand help with no
  descriptions or examples, `--limit` documented on `analyze` but consumed only
  by `merchants`, inconsistent null rendering and summary formats across
  surfaces, `sources` counting per-row provenance while reading as "files
  ingested". judge-frontend-ux P4-P7 only, all directly observed.
- **PD13 — Setup friction.** Five manual `cp` steps and an environment variable
  before the first command, with no `init` subcommand. judge-backend,
  judge-product-agentic F7, judge-security-ops F3. judge-backend and
  judge-security-ops both name `fin init` as their `product` improvement.

### Credible risks

- **PR1 — `fin sql` executes arbitrary DuckDB on a default connection.** No
  read-only mode, no statement-kind check, no `enable_external_access = false`.
  judge-security-ops F9 and judge-product-agentic F3 both rate it the highest-
  consequence item in their reports, on the specific ground that the analyze
  skill steers a model toward it and the descriptors the model reasons over
  arrive from files the user did not author. Both state explicitly that they did
  not attempt an exploit. judge-backend and judge-frontend-ux observed the same
  code and rated it low impact. See Material disagreements.
- **PR2 — Non-atomic cross-table writes after the all-or-nothing gate.**
  `ingest_card_file` performs three independent whole-table writes; a failure
  between them leaves transactions whose source records do not exist, and
  `validate.py:45` checks only the opposite direction, so that torn state passes
  validation clean. judge-backend F8 and judge-security-ops F10 reached this
  independently, including the same blind spot in `validate`.
- **PR3 — Dispute deadlines are computed against the ledger's latest post date,
  not today.** judge-product-agentic F1, single judge, from source. He rates it
  "the most consequential issue in the submission: it is silent, it is on by
  default, and it produces a confidently wrong number on the output with a legal
  clock," and notes the `EXPIRING` bucket the skill tells the agent to surface
  first would never fire. See Material disagreements for the tension with the two
  judges who praised the same ledger-relative clock in the detector layer.
- **PR4 — `cmd_ingest` returns 0 after `_revalidate` reports invariant problems
  to stderr.** judge-frontend-ux K1, single judge, from source, no scenario
  produced a failing invariant. He calls it "the worst failure mode in this
  list" because it is the only machine-readable signal an agent or script has.
- **PR5 — Sign-blind amount matching.** `build_edges` compares absolute values
  over a candidate set that includes refunds, so a refund and an equal-amount
  purchase days apart are a tier-1 match on a system whose premise is that
  refunds land later under different descriptors. judge-backend F6, single judge,
  unexercised.
- **PR6 — Unreachable tier 3.** Subset-sum edges are appended after `resolve()`
  has run, so a subset-sum explanation can only emerge as `AMBIGUOUS`, never as a
  committed `SUBSET_SUM` match, while the engine's own tier table, the README and
  the fin-reconcile skill all present it as a match tier. judge-backend F2 and
  judge-product-agentic F6 agree on the mechanism and disagree on the
  classification: judge-backend records it as a confirmed docs/implementation
  mismatch established by static read, judge-product-agentic declines to call it
  a defect because tier 3 was never exercised and notes the failure direction is
  safe.
- **PR7 — Permission model applied inconsistently, and chmod failures are
  swallowed.** Only the vault root carries an explicit mode; ledger JSONL files
  and subdirectories rely on it. judge-security-ops F15 adds that `OSError` on
  chmod is swallowed, so on a filesystem that cannot chmod the privacy guarantee
  degrades silently. judge-backend F10 records the same inconsistency and
  explicitly does not count it against a score. judge-frontend-ux and
  judge-product-agentic record it as the manifest's R14 scope caveat rather than
  a defect.
- **PR8 — No action-level observability.** Nothing records which command an agent
  chose, with what arguments, before a ledger mutation. judge-product-agentic F8
  and judge-security-ops F6 count it against `agentic`. judge-backend and
  judge-frontend-ux R4 record the same absence and explicitly decline to penalize
  it for a single-user local CLI. An agreed fact scored two ways.
- **PR9 — Unmeasured worst-case enumeration and unobserved scale.** Subset-sum
  enumerates combinations up to `MAX_EXHAUSTIVE_ITEMS = 20` with no measurement
  anywhere in the package (judge-backend), and the largest ledger in the entire
  evidence package is four rows, so nothing about behaviour at the stated scale is
  observed (judge-security-ops).
- **PR10 — `op run --env-file=.env` places resolved secrets in the environment of
  a process that reads exactly one variable, `FIN_DATA_DIR`.** judge-security-ops
  F13, single judge, from README and `ev-ledger-20`.
- **PR11 — `fin dispute` with no selector builds a packet over the entire
  ledger.** judge-product-agentic F11, single judge, from source.
- **PR12 — A missing `pdftotext` reports as "no adapter recognises" rather than
  as a missing dependency**, because `sniff` catches bare `Exception`.
  judge-security-ops F12, single judge, unexercised since the image has the
  binary.

## Material disagreements

`atj score` classified every criterion as aligned, and the deterministic result
records no material or severe disagreement, no possible outlier, and no required
adjudication. The items below are interpretive divergences inside the aligned
band. They are reported as divergences rather than averaged, and no judge's score
was adjusted.

- **M1 — What counts as the product surface (`product`, range 1.0).**
  judge-frontend-ux scored the live command surface and reached 3 with high
  confidence. judge-backend, judge-product-agentic and judge-security-ops
  weighted problem fit and the generated reports and reached 4, two of them with
  medium confidence, while naming the same traceback defect. Cause: persona
  emphasis and a genuine difference in what a CLI's usability consists of. No
  factual contradiction. Resolution: recorded, minority view preserved.

- **M2 — What unobserved agent effectiveness should cost (`agentic`, range
  1.0).** judge-backend and judge-frontend-ux at 3; judge-product-agentic and
  judge-security-ops at 4. All four agree effectiveness is unobserved and agree
  it is unobservable under the event's no-network constraint. The split is over
  whether design plus control, verified against artifacts, is enough to hold a 4
  when the instruction text contains errors that contradict the implementation.
  judge-product-agentic pre-registered the counterfactual: if the panel weights
  demonstrated agent behaviour heavily, his score belongs a point lower.
  Resolution: recorded. The panel should note this is the criterion where the
  event's constraint, not the submission, sets the evidence ceiling.

- **M3 — Severity of the `fin sql` surface (no score divergence).** Two judges
  rate it the top risk in the submission; two rate it low impact. The disagreement
  is entirely about threat model, not about the code, which all four read.
  judge-backend: "Arbitrary SQL is the advertised feature and the only data
  reachable is the user's own, so impact is low." judge-frontend-ux treats it as a
  diagnosability annoyance (K2). judge-security-ops: "The delta that matters is
  the agent," tracing a path from attacker-influenced descriptor text through a
  model-composed query to filesystem and network access from a process the product
  advertises as offline. judge-product-agentic reaches the same conclusion
  independently. Both risk-side judges state they attempted no exploit. This is
  the panel's widest substantive gap and it is invisible in the score table, since
  `security` is unanimous at 4.0.

- **M4 — Whether a ledger-relative as-of date is a strength or a defect.**
  judge-backend and judge-security-ops both cite `detectors.py:36-37` reading

## Prioritized improvements

Ordered by how many judges independently nominated the item as their top or
near-top fix, and by whether the item changes a user's results rather than their
experience. Each judge's own highest-value nomination is preserved below the
list.

1. **Make the tier-0 documentation match the implementation (PD2).** Add
   `external_ref` to the documented column list in `amazon.py`, the fin-ingest
   skill and the README, fix the contradicting comment, and warn from
   `ingest-amazon` when a feed carries no `external_ref` column.
   judge-frontend-ux's top fix, confirmed by all four judges, and the only
   confirmed defect on this list that silently degrades a real user's results.
2. **Give `src/fin/dispute.py` tests across the close-date boundary (PD4).** One
   case per state, the `EXPIRED` re-tag to `UNAUTHORIZED_USE`, and a multi-month
   `interest_attribution` carry, with a fixed as-of. judge-backend estimates
   roughly forty lines. judge-product-agentic's `reliability` nomination and
   judge-backend's close second overall.
3. **Constrain `fin sql` (PR1).** Reject anything that is not a single
   `SELECT`/`WITH`, set `enable_external_access = false` and lock the
   configuration before executing. judge-security-ops' top fix overall and
   judge-product-agentic's `agentic` and `security` nomination. Note M3: two
   judges consider this low impact.
4. **Fix the reclassification path (PD7).** A re-derivation pass when the rules
   file changes, or a `fin reclassify` command. judge-backend: "the honest
   interim fix is deleting that paragraph from the skill." His top fix overall,
   raised by him alone.
5. **Default the dispute as-of date to today (PR3).** Keep `--as-of` for
   reproducible runs and print the as-of date in the terminal summary and as a
   CSV column. judge-product-agentic's top fix overall, raised by him alone, and
   in tension with M4.
6. **Unify the ingest rejection contract (PD1).** Convert the two adapter
   `ValueError` raises to `IngestRejected`, or add a top-level handler in
   `main()`. Named by all four judges, described by two of them as a two-line
   fix. judge-security-ops' and judge-product-agentic's `engineering`
   nomination.
7. **Make the matches table honest and decide tier 3's status (PD3, PR6).** Give
   `UNMATCHED` a `NONE` method, and either wire subset-sum through `resolve()` so
   it can commit or state that the system does not reconcile split shipments.
   judge-backend: "A half-built tier that advertises a capability is worse than an
   absent one."
8. **Return non-zero when post-ingest revalidation finds problems (PR4), and add
   the reverse orphan check to `validate` (PR2).** judge-frontend-ux's
   `reliability` nomination and judge-security-ops' `reliability` nomination
   respectively. Together they close the only failure state ingest can produce
   undetected and the only machine-readable signal that is currently wrong.
9. **Make the unexercised paths observable.** A committed fixture PDF or a
   `--from-text` flag for the CLI path (judge-security-ops), one scenario with an
   amount-and-date collision so `AMBIGUOUS` can be seen (judge-frontend-ux), one
   dispute run against an ingested statement (judge-product-agentic), and a
   fixture ledger demonstrating D0 firing on transaction one while the
   statistical detectors stay silent (judge-security-ops).
10. **Add `fin init` and an append-only invocation log.** `fin init` removes the
    only hard onboarding step (judge-backend, judge-security-ops). An
    append-only `audit.jsonl` of subcommand, arguments, exit code and row counts
    turns the agent layer from unobservable into reviewable (judge-security-ops,
    judge-product-agentic F8). judge-security-ops estimates twenty lines.
