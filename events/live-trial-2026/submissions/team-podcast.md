# Submission Intake — Podcast Listener

`atj intake` materialized this submission and pinned it. The sections below are the team's own account of what they built; the tool does not supply them.

## Team statement

The README states this is "a self-hosted podcast player for your own `.m4a`
files, installable on an iPhone home screen, with offline downloads and resume
tracking" (`README.md:1-2`). `DECISIONS.md`'s Context section frames the goal as
playing "a private, growing library of `.m4a` files on an iPhone with resume
tracking and full offline playback (hard requirement)" for a single listener —
the team member who owns the source library (`DECISIONS.md`, Context; D11 "No
authentication... the tailnet is the perimeter").

The source audio is a private collection of AI/engineering podcast episodes
generated by Google NotebookLM (`DECISIONS.md`, Context: "Google NotebookLM
output"). This is explicitly not a public-podcast client: RSS subscriptions,
OPML and multi-user support are named as out of scope (`DECISIONS.md` D14). The
team frames the problem as: their own recordings have no usable ID3/metadata
tags and no reliable release date, are too large in total to fit an iPhone
untranscoded, and need to survive a dropped network connection mid-episode —
each of those is addressed by a corresponding decision in `DECISIONS.md` (D1
transcoding, D3/D4 OPFS + blob-URL offline storage, D20/D21 release-date
lookup).

I did not independently verify the "working, deployed... verified on a physical
iPhone" claim on the README's status line (`README.md:6-7`) — that is the
team's own account of on-device testing, not something this intake observed.

## Primary workflows

Inferred from the FastAPI routes in `server/app.py`, the SQL in `server/db.py`,
and the DOM event bindings in `web/js/app.js`:

1. **Browse the library.** The client loads episodes from `GET /api/library`
   (`server/app.py:81-86`, backed by `server/db.py`'s `library()` query, which
   orders `COALESCE(released_at, created_at) DESC`) and renders them as a list
   (`web/js/app.js`, `loadLibrary()` starting around line 41). The list also
   renders from an IndexedDB mirror when offline (`web/js/app.js:44-49`,
   `web/js/idb.js`).
2. **Play an episode.** Clicking a row (`web/js/app.js:148`,
   `main.onclick = () => void player.toggle(ep)`) starts playback through
   `web/js/player.js`, a plain `<audio>` element plus the MediaSession API. If
   the episode is not downloaded, audio streams from
   `GET /api/media/{episode_id}`, which serves byte-range (`206`) responses for
   seeking (`server/app.py:141-199`).
3. **Download an episode for offline playback.** The per-row download button
   (`web/js/app.js:186`, `startDownload`) writes the audio into OPFS via a
   dedicated Web Worker (`web/js/opfs-worker.js`), because Safari's
   `createWritable()` is unsupported and `createSyncAccessHandle()` is
   worker-only (`DECISIONS.md` D3). Playback then reads from a `blob:` URL
   instead of the network.
4. **Delete a download.** A per-row delete control (`web/js/app.js:179`,
   `deleteDownload`) and a bulk "Delete downloads" button
   (`web/js/app.js:356`, `deleteAllDownloads`) remove OPFS entries; the library
   entry itself is untouched (`README.md`, "Managing downloads").
5. **Track and resume listening progress.** The client pushes position via
   `PUT /api/progress/{episode_id}` (`server/app.py:104-112`) on pause/end/
   visibility-change and reads it back via
   `GET /api/progress/{episode_id}` (`server/app.py:115-117`), with an
   IndexedDB mirror and last-write-wins conflict resolution on `updated_at`
   (`server/db.py`, `put_progress()`; `DECISIONS.md` D8, D9).
6. **Filter and sort the list.** "Hide played" (`web/js/app.js:349`,
   `playedBtn.onclick`) and "Downloaded only" (`web/js/app.js:343`,
   `dlBtn.onclick`) toggle client-side filters that persist in
   `localStorage`; the underlying order is always newest-release-first.
7. **Add new episodes / rescan.** The "Rescan" button
   (`web/js/app.js:363`) calls `POST /api/rescan`
   (`server/app.py:89-93`), which transcodes any new files in `source/` via
   `server/media.py` and re-indexes the library.
8. **Regenerate release dates (maintainer-only, offline).**
   `scripts/sync-releases.py` joins a separate blog repo's `posts.json` and
   `audio-map.yaml` on exact filename and writes the committed
   `releases.json`; this is a one-off maintenance step, not a user-facing
   workflow in the running app.

## Run instructions

**Prerequisites** (per `README.md`, Setup): `ffmpeg`, `ffprobe`, Python 3.11+,
and `git-lfs` (the `source/**/*.m4a` files are Git-LFS-tracked, see
`.gitattributes`). `uv` is used if present, otherwise `run.sh` falls back to
`python3 -m venv`. I confirmed the checkout's `source/` directory already
holds real audio, not LFS pointer stubs (`file source/*.m4a` reports
"ISO Media, MPEG v4 system..."), so LFS has already been materialized here —
56 files, ~2.2 GB by direct measurement (see Known limitations for the
discrepancy against the README's stated 33 files / 1,360 MB).

**Start:** `./run.sh` (`run.sh:1-58`). On first run it creates `.venv` and
installs `fastapi` and `uvicorn[standard]`, transcodes any new source files
via `.venv/bin/python -m server.media`, then execs
`uvicorn server.app:app --host 0.0.0.0 --port 8000`. `./run.sh --https` instead
serves `:8443` with a self-signed cert generated by `gen-cert.sh` (creates
`certs/ca.crt` and `certs/server.crt`, gitignored). No `.env` file is required —
all settings have working defaults; optional overrides
(`PODCAST_SOURCE_DIR`, `PODCAST_MEDIA_DIR`, `PODCAST_DB_PATH`,
`PODCAST_BITRATE`, `PODCAST_CHANNELS`) are documented by variable name in the
README's Configuration table (`README.md`, "Configuration"); I could not read
`.env.example` itself — a project hook denied reading that path — so this
list is drawn from the README's own documentation of it, not a direct read of
the file.

**Ports:** `8000` (HTTP, default) or `8443` (HTTPS, `--https` flag). The
production deployment additionally fronts port 8000 with `tailscale serve`
(`README.md`, "Currently deployed"), which is outside this checkout's scope.

**Test data:** the audio in `source/` is the only test data needed; `run.sh`
transcodes it into `data/media/` (gitignored, derived, safe to delete) and
indexes it into `data/app.db` (SQLite, gitignored) on every startup
(`server/app.py`, `index_library()` / `lifespan`).

**Test suite:** `tests/e2e.py`, a Playwright script (`tests/requirements.txt`:
`playwright>=1.50`). Per `README.md` ("Tests"):

```sh
uv pip install --python .venv/bin/python -r tests/requirements.txt
./run.sh                                                     # in one terminal
.venv/bin/python tests/e2e.py                                # localhost, in another
```

`tests/e2e.py` hardcodes `CHROMIUM = "/usr/bin/chromium"` (`tests/e2e.py:26`)
and launches it directly rather than via Playwright's bundled browser
download — if no chromium binary exists at that path in the sandbox, the
script will fail at `browser = p.chromium.launch(...)` before exercising any
application behavior, which is an environment gap rather than an application
defect. The script prints one `[PASS]`/`[FAIL]` line per check and a final
`N/M checks passed` summary, and its `main()` returns a non-zero exit code if
any check failed (`tests/e2e.py`, end of `main()`). It takes an optional base
URL argument for testing against a non-localhost deployment; no other
arguments or config are needed.

None of this was executed as part of this intake.

## AI and external services

**No AI/LLM API calls in the running application.** I read every server module
(`server/app.py`, `server/config.py`, `server/db.py`, `server/media.py`) and
every client script (`web/js/app.js`, `player.js`, `storage.js`,
`opfs-worker.js`, `idb.js`, `web/sw.js`) and searched them for outbound network
calls: the only `fetch()` calls target same-origin paths
(`/api/library`, `/api/progress/{id}`, `/api/rescan` in `web/js/app.js` and
`player.js`; a source-audio fetch inside `web/js/opfs-worker.js:28` that is
also same-origin, into the app's own `/api/media/` path). There is no import
of an HTTP client in the server code that targets a third-party host, and no
model, API key, or AI SDK reference anywhere in `server/` or `web/`.

**The source audio's origin, not the app, involves AI.** `DECISIONS.md`'s
Context section states the source `.m4a` files are themselves the output of
Google NotebookLM — that describes how the team produced the content before
this app existed, not a runtime dependency of the submitted code.

**Git LFS is required to materialize the audio at checkout time**
(`.gitattributes`: `source/**/*.m4a filter=lfs`), which needs network access to
the LFS remote *before* `./run.sh` starts. This checkout already has real audio
files, not pointer stubs, so that step is already done here.

**`scripts/sync-releases.py` requires a second, unrelated local checkout**
(`BEEKEEPER_WEBSITE_DIR`, defaulting to
`~/Nextcloud/workspace/beekeeper-lab_website`) holding a private blog repo's
`posts.json` and `audio-map.yaml`. That checkout will not exist in the
sandbox, so this script cannot run there — but it is a maintainer-only
regeneration step, not something `run.sh` or the running app calls;
`releases.json`, its output, is already committed.

**The team's target deployment needs the network the event sandbox does not
provide.** README and DECISIONS.md describe the real usage path as an
installed iPhone PWA reached over `tailscale serve` HTTPS
(`README.md`, "Getting it onto the iPhone"; `DECISIONS.md` D10, D6). Service
workers and OPFS require a secure context, and `localhost` is the one
exemption (`README.md`). With the event's empty network allowlist and no
egress: `./run.sh` on plain HTTP at `http://127.0.0.1:8000` needs no network
and should work as-is; anything that depends on Tailscale (the HTTPS proxy,
the `forge.tailaa5efd.ts.net` name, `gen-cert.sh`'s Tailscale-name lookup) or
on a physical iPhone cannot be exercised. That makes PWA-install-to-home-screen,
background audio with the phone locked, and real iOS storage-quota/`persist()`
behavior evidence-limited to the team's own README/DECISIONS.md claims rather
than independently reproducible in this event.

**No credentials are used.** The only configuration surface is a small set of
local filesystem paths and transcode parameters (see Run instructions); none
of the documented `.env` variable names correspond to a secret or API key.

## Known limitations

- **README numbers don't match this checkout.** `README.md:6` states
  "Source: `source/` 33 files · 11.7 h · 1,360 MB". I counted directly:
  `source/` in this checkout holds 56 `.m4a` files totaling ~2.2 GB
  (`find source -name '*.m4a' | wc -l` → 56; `du -sh source` → 2.2G).
  `releases.json` (committed) lists 41 dated releases and 15 unresolved
  entries, which sums to 56 — consistent with the checkout, not with the
  README's 33. This looks like a stale figure the team did not update after
  adding episodes; evaluators should treat the README's counts as an outdated
  team claim, not the current state.
- **Internal inconsistency in the team's own pass counts.** `README.md:7`
  claims "34/34 automated checks pass" in the top status line, while
  `README.md:285` ("Both targets pass 42/42") and `DECISIONS.md:9`
  ("42/42 desktop end-to-end checks pass") both say 42/42. `tests/e2e.py`
  itself contains 43 `check(...)` call sites. I did not run the suite, so I
  cannot say which figure (if any) is current — only that the document is
  internally inconsistent.
- **All "Confirmed"/"Verified" claims are team claims, not observations made
  here.** The README's Verification status table and DECISIONS.md's
  "On-device status" (background audio with the screen locked on a physical
  iPhone, OPFS + range requests + progress resume, HTTPS via Tailscale with a
  real Let's Encrypt cert) describe the team's own manual and device testing.
  No execution was performed as part of this intake, so none of it is
  independently confirmed here.
- **Two items the team itself marks unverified:** real iOS storage quota and
  whether `navigator.storage.persist()` grants (README "Verification status";
  DECISIONS.md "On-device status" — "Not yet measured"/"still unmeasured"),

- **iPhone-specific and HTTPS-dependent behavior cannot be reproduced under
  the event's no-egress sandbox** (see AI and external services above):

  it. This is the team's own disclosure about a different, not-submitted
  component (the deployed app here has no such public route and is
  unauthenticated only within a private tailnet, per D11); it does not apply
  to the code in this checkout, and I am reporting it only because
  `DECISIONS.md` is part of the submission.
- **`scripts/sync-releases.py` cannot be exercised in this or the sandbox
  environment** — it requires a second local checkout of an unrelated blog
  repository that will not exist. `releases.json`, its output, is already
  committed, so this only blocks *regenerating* release dates, not running
