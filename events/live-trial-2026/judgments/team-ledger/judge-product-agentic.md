# Individual Judgment

## Executive assessment

Hive Ledger is a real product built on one clear and unusual product decision:
the system's output is the set of charges it *cannot* explain, and every
component is built to refuse rather than to guess. That decision is not
marketing — it is visible in the executed behavior. Ingest refuses four
different malformed inputs and leaves every table empty
(`runs/team-ledger-ingest-integrity-01.json`). The matcher refuses to optimize
and commits only edges unique from both sides
(`src/fin/match/engine.py:98-138`). D1 refuses to draw a conclusion from a
missing merchant feed and says so instead
(`src/fin/detect/detectors.py:120-138`, observed in
`runs/team-ledger-analyze-render-dispute-01.json`). A CSV load labels itself
`UNVERIFIED (no control totals)` rather than implying it was proven. That
consistency between a stated principle and observed behavior is the strongest
thing in this submission.

The AI allocation is the right one and it is structurally enforced rather than
promised: no model API, HTTP client, or network import exists anywhere in the
22-file `fin` package ([[evidence:ev-ledger-20]]), so arithmetic and parsing
cannot silently become model output. The model's job is routing and
explanation, plus one narrow fuzzy task (proposing merchant rules) that a human
approves and that is then frozen into deterministic config
(`.claude/skills/fin-analyze/SKILL.md:54-78`). That is AI used where it helps
and excluded where it would hurt.

Two things hold it back. First, the dispute clock — the one output with a
real-world consequence — computes deadlines against the latest post date in the
ledger instead of today (`src/fin/cli.py:174`, `src/fin/analyze/spend.py:141`),
and the module that does it has no tests and was never observed producing any
state except `NO_STATEMENT`. Second, the agent layer is entirely unevidenced as
behavior, and one of the tools it is told to reach for (`fin sql`) is an
unconstrained DuckDB session. Everything else the model can do is a narrow,
audited verb; that one is not.

## Criterion findings

### functional — Functional correctness and completeness

**Evidence.** Direct observation across eleven sandboxed run records. All ten
subcommands exist and their help matches the documented surface
([[evidence:ev-ledger-01]], `runs/team-ledger-cli-help-01.json`). CSV ingest,
`status`, `detect`, `validate` ([[evidence:ev-ledger-02]],
[[evidence:ev-ledger-03]]); four rejection paths with nothing written, then
idempotent re-ingest ([[evidence:ev-ledger-04]],
`runs/team-ledger-ingest-integrity-01.json` stdout `1 new` then `1 already
known`); Amazon ingest, tier-0 and tier-1 matching, `sql`, `detect`, `validate`
([[evidence:ev-ledger-06]]); all four `analyze` modes, `render`, `dispute`
([[evidence:ev-ledger-07]]); PDF line grammar against both a balanced and an
unbalanced synthetic statement, with the control-total gate rejecting the
latter ([[evidence:ev-ledger-08]], [[evidence:ev-ledger-09]]). Every advertised
primary workflow ran and exited 0.

**Strengths.** The gate does what the README says it does, and it was proven
against an input engineered to break it: a $500 declared payment with no
matching row is rejected with the exact discrepancy named
(`runs/team-ledger-pdf-grammar-01.json`). Idempotence, no-partial-import, and
invariant re-assertion after mutation are all observed rather than asserted.

**Deficiencies.**

- **F2 (major).** `src/fin/dispute.py` produced only `NO_STATEMENT` items in the
  one dispute run (`runs/team-ledger-analyze-render-dispute-01.json` stdout:
  `no_statement 2`), and the test index shows no test function touching dispute
  at all (`tests/test_properties.py`, 31 `test_` functions, none naming
  dispute, deadline, or claim). The `OPEN`/`EXPIRING`/`EXPIRED` branches at
  `src/fin/dispute.py:67-76`, including the re-tag to `UNAUTHORIZED_USE` that
  `.claude/skills/fin-dispute/SKILL.md:38` calls "the single most important
  behaviour in this skill", are neither executed nor tested anywhere in this
  package. This is an unexercised branch on the headline path, not an absent
  feature — I do not treat it as failure, but it is the largest unproven claim
  in the submission.
- **F6.** Tier-3 subset-sum edges are appended directly to the contested map
  after `resolve()` has already run (`src/fin/match/engine.py:249-257`), so a
  subset-sum explanation can only ever emerge as `AMBIGUOUS`, never as a
  committed `SUBSET_SUM` match. The README tier table
  (`README.md:106-112`) and the engine docstring both present tier 3 as a match
  tier with confidence 0.50-0.70. Inference from source; tier 3 was not
  exercised, so I cannot call it a defect. The direction is safe (it
  under-commits, consistent with the product principle) but the documentation
  and the implementation disagree.
- **F9.** Documentation says the Amazon transactions feed's `order_id` is "what
  makes tier-0 matching possible" (`.claude/skills/fin-ingest/SKILL.md:55-58`).
  The run record contradicts the mechanism directly: of two merchant charges,
  the one carrying `external_ref=A1B2C3D4E` matched `REFERENCE` at 1.0 and the
  one with an empty `external_ref` but a populated `ORDER-0002` fell through to
  `AMOUNT_DATE_UNIQUE` (`runs/team-ledger-amazon-match-detect-01.json`). Tier 0
  keys on `external_ref`, not `order_id`. Corroborates
  [[evidence:ev-ledger-16]].

**Rationale.** Every promised workflow was demonstrated end to end on synthetic
data, with the hard cases (rejection, idempotence, control totals) deliberately
targeted. That is a 4. It is not a 5 because the dispute state machine, the
ambiguity tier, and the subset-sum integration — three of the more
consequential paths — are unexecuted and in two cases untested, and because the
CLI-level PDF path was never invoked.

**Uncertainty.** Medium. The PDF-file gap is narrow and well-characterized (the
grammar was tested directly, `pdftotext` confirmed present at
`/usr/bin/pdftotext`), so I weight it lightly. The dispute-clock gap I weight
heavily because nothing in the package — not a run, not a test — touches it.

**Highest-value improvement.** Produce one dispute run against an ingested
statement so `OPEN`, `EXPIRING`, and the `EXPIRED` re-tag actually execute.

### product — Product value and usability

**Evidence.** Team claim (intake "Team statement", `README.md:13-32`): the
motivating incident was 201 unauthorized Amazon charges over 343 days. Not
independently verifiable and I do not score it as fact. What *is* observable is
that the design answers that specific problem rather than a generic one.
Direct observation of output quality:
`runs/team-ledger-analyze-render-dispute-01.json` shows a variance table that
prints `--` for a category with no target rather than implying compliance, a
findings report that reproduces the verbatim descriptor and date of each
flagged charge, a D1 finding that states the feed is missing instead of
reporting a 0% match rate, and a dispute CSV carrying descriptor, account,
claim type, and state per row.

**Strengths.** The product decisions are unusually disciplined and they survive
into the artifacts a user actually reads. "The product is not the matched set,
the product is the unmatched set" is a defensible inversion of the obvious
metric, and D0 is the cleanest expression of it: five lines of declared config
catch on transaction one what the statistical detectors need six months to
suspect (`src/fin/detect/detectors.py:55-102`, fired correctly in two separate
runs). Honest labeling is consistent — `UNVERIFIED (no control totals)`,
`NO_STATEMENT`, `deadline: unknown`, and a generated-file banner on every
rendered report.

**Deficiencies.**

- **F1 (major).** `fin dispute` defaults its as-of date to the latest post date
  in the ledger (`src/fin/cli.py:174` to `src/fin/analyze/spend.py:141-142`,
  `max(post_date, default=today)`). Deadlines and `days_left` are therefore
  computed against the data's age, not the real date. A user who last ingested
  three months ago is shown a charge as `OPEN` with positive days remaining
  when the 60-day billing-error window has actually closed, and the `EXPIRING`
  bucket that `.claude/skills/fin-dispute/SKILL.md:42-46` tells the agent to
  surface first never fires. The markdown packet does print `**As of:** <date>`
  (`src/fin/render.py:193`), but the terminal summary does not and the CSV has
  no as-of column (`src/fin/dispute.py:116-147`). The reproducibility argument
  that justifies a ledger-relative clock for detectors
  (`src/fin/detect/detectors.py:3-5`) is the wrong trade for a statutory
  deadline. Inference from source, high confidence in the mechanism.
- **F4.** Two of four ingest rejections print a clean `REJECTED <file>:
  <reason>`; the other two dump a full Python traceback
  (`runs/team-ledger-ingest-integrity-01.json` stderr, from
  `src/fin/adapters/citi_csv.py:54,70` raising bare `ValueError` which
  `src/fin/cli.py:cmd_ingest` does not catch). Directly observed. Nothing is
  imported either way, so this is a usability defect, not a data defect — but
  rejection is this product's signature behavior and half of that surface looks
  like a crash.
- **F5.** `UNMATCHED` links are stamped `method="AMOUNT_DATE_UNIQUE"` with
  confidence 0.0 (`src/fin/match/engine.py:283`), which surfaced verbatim in
  user-visible output: `AMOUNT_DATE_UNIQUE | UNMATCHED | 0.0`
  (`runs/team-ledger-amazon-match-detect-01.json`). In the one table the
  product says matters most, the unmatched row is labeled with a match method.
  A user grouping `matches` by method gets a wrong answer.
- **F7.** First run requires five manual `cp` steps plus `FIN_DATA_DIR` or
  `--data-dir`, and there is no `init` subcommand (`src/fin/cli.py:248-290`
  defines ten subcommands, none of them setup). For a stated audience of one
  individual managing their own cards, that is avoidable friction.
- **F10.** The D1 title reads "1 of 3 merchant-feed charges on
  citi-costco-4021 are unexplained" (`src/fin/detect/detectors.py:158`) when the
  three items are card charges belonging to a feed-declared family, not charges
  from the merchant feed. Minor, but the skill instructs the agent to relay this
  text to the user.
- **F11.** `fin dispute` with no `--detector`/`--merchant`/`--account` selects
  every transaction in the ledger (`src/fin/cli.py:159`) and writes a packet.
  Risk, not observed.

**Rationale.** The problem is real and specific, the solution is understandable
in its output, and the hard product judgments (refuse to guess, name what you
cannot conclude, never write off an old charge) are carried through into code
and visible text. That clearly exceeds normal expectations. It is not a 5
because the deadline clock is wrong by default on the output with the highest
stakes, and because two of the user-facing surfaces (rejection messages, the
unmatched table) are rougher than the rest of the product.

**Uncertainty.** High confidence. Every point above is either in a run record's
stdout/stderr or in a named source line.

**Highest-value improvement.** F1: default the dispute as-of date to today,
keep `--as-of` for reproducible runs, and print the as-of date in the terminal
summary and as a CSV column.

### agentic — Agentic and AI system design

**Evidence.** Artifact evidence, four skill files read as data:
`.claude/skills/{fin-ingest,fin-reconcile,fin-analyze,fin-dispute}/SKILL.md`.
Direct observation that no model or network surface exists in the deterministic
core ([[evidence:ev-ledger-20]]: zero LLM/HTTP imports or call sites across 22
files; the only `subprocess` use is `pdftotext`; the only environment read is
`FIN_DATA_DIR`). Direct observation of the tools the agent is told to call
(`src/fin/cli.py`, all ten verified by `runs/team-ledger-cli-help-01.json`).

**Strengths.** The allocation of work between model and code is the correct one
and is enforced by construction, not by instruction: money, parsing, matching,
and gating are in tested Python that the model cannot reach into, and the model
selects commands and explains results (`src/fin/cli.py:1-7`). The skills are
better than typical prompt text in four specific ways:

1. **Routing boundaries are explicit and mutual.** Each `description` states
   both when to use the skill and which sibling skill owns the adjacent case
   ("Do NOT use to analyze... that is fin-reconcile and fin-analyze"). That is
   the part of multi-skill design that usually goes missing.
2. **Refusal rules are aimed at the model's known failure modes.** Never
   transcribe a figure out of a PDF by hand
   (`fin-ingest/SKILL.md:16-20`); do not retry a rejection with a flag or import
   "just the good rows" (`fin-ingest/SKILL.md:68-73`); never describe a charge
   as fraudulent (`fin-reconcile/SKILL.md:81-83`); never state that an expired
   billing-error window extinguishes a claim (`fin-dispute/SKILL.md:66-68`);
   say the deadline arithmetic is a calculation, not legal advice. These are
   guardrails against a confident model doing damage in a money and quasi-legal
   context, and they are specific enough to be checkable.
3. **The one fuzzy task has a real human-in-the-loop and a termination
   condition.** The model proposes merchant rules, the user approves, the rule
   is frozen into `config/merchant-rules.yaml` and applied deterministically
   forever (`fin-analyze/SKILL.md:54-78`). Judgment used once, reviewed, then
   retired. The skill also states the correction path (re-ingest, never
   hand-edit a category) and why (`fin-analyze/SKILL.md:70-78`).
4. **The agent is told to prefer the exact tool over reasoning.** "Reach for
   `fin sql` ... rather than reading the JSONL into context and aggregating by
   hand. A query is exact, cheap, and reproducible; mental arithmetic over a
   thousand rows is none of those" (`fin-analyze/SKILL.md:31-33`). The CLI
   backs this up: `fin detect` and `fin match` output the same numbers the
   reports render, so the model has nothing to recompute.

**Deficiencies.**

- **F3 (major).** `fin sql` is the one unconstrained tool in the set, and the
  skill actively steers the model toward it. `src/fin/cli.py:209-230` opens a
  default `duckdb.connect()` and executes the query string verbatim: no
  read-only mode, no `SET enable_external_access=false`, no statement-kind
  check, no confirmation. DuckDB's default configuration permits `COPY ... TO
  '<path>'` and `read_csv_auto('<path>')`, so a model-composed query can write
  and read outside the vault with the user's full permissions. The injection
  route is not hypothetical: `descriptor_raw` comes from untrusted statement and
  merchant-export files, is stored verbatim, and is surfaced to the agent in
  `fin detect` and report output (observed in
  `runs/team-ledger-analyze-render-dispute-01.json`). A crafted descriptor is
  content the model reads before composing a query. Credible risk, not a
  demonstrated exploit — no run attempted one.
- **F8.** Nothing records what the agent did. The store keeps excellent
  provenance for *data* (source file, sha256, line number, raw line —
  `src/fin/ingest.py:207-217`) and none at all for *actions*: no log of which
  command was invoked, by whom or what, with which arguments, before a ledger
  mutation. For an agent-driven money system, the question "why does the ledger
  look like this?" is answerable for rows and unanswerable for decisions.
  Inference from source; I found no logging module in the package.
- **Effectiveness is unevidenced.** The agent loop cannot run in a no-network
  sandbox, which is an event constraint and not the team's fault. But the team
  also shipped no recorded session, no skill-routing test, and no evaluation of
  any kind for the layer. Nothing in the repository would tell the team if a
  skill stopped routing correctly.

**Rationale.** I score this, rather than `NE`, because the criterion's question
— is AI appropriate, controlled, effective — is substantially answerable from
artifacts, and three of the four sub-questions are. Appropriateness is not just
argued but proven by the absence of any model in the money path. Control is
strong at the instruction layer and strong for nine of the ten tools. Against
that: observability is absent (F8), one tool is unconstrained (F3), and
effectiveness is unproven. A 4 reflects a design that is clearly better
reasoned than a typical agent wrapper, held below 5 by the fact that the agent
half of the system has no feedback loop of any kind.

**Uncertainty.** Medium. My assessment of the design rests on reading
instruction text; my assessment of its effect on a real session rests on
nothing. If the panel weights demonstrated agent behavior heavily, this belongs
a point lower, and I would not argue hard against that.

**Highest-value improvement.** F3: run `fin sql` read-only — `SET
enable_external_access=false` plus a rejection of anything that is not a single
`SELECT`/`WITH` — so the one wide tool handed to the model becomes as narrow as
the other nine.

### engineering — Engineering and maintainability

**Evidence.** Source read at the pinned commit: `src/fin/store.py`,
`ingest.py`, `validate.py`, `match/engine.py`, `detect/detectors.py`,
`dispute.py`, `cli.py`, `adapters/citi_pdf.py:1-40`, `analyze/spend.py`
excerpts.

**Strengths.** Module boundaries match the problem shape and nothing is
over-built. Integer cents throughout with no float
(`src/fin/store.py`, `money.py` per tests). Content-derived ids make
idempotence a property of the id scheme rather than a check
(`src/fin/ingest.py:12-16, 186`). Writes are atomic tmp-then-replace with
deterministic sort order (`src/fin/store.py:109-121`), so the ledger diffs
cleanly. Derived tables are rewritten wholesale so a stale run cannot leave
phantom findings (`src/fin/store.py:47-49`). The docstrings are the best part:
they state the rejected alternative and why, including why prefix matching is
refused in D0 (`detectors.py:40-49`), why merging is only correct across
sources (`ingest.py:174-183`), and why there is no global optimizer
(`engine.py:12-17`). That is the documentation that keeps a maintainer from
"fixing" a deliberate behavior.

**Deficiencies.** F4 (inconsistent error contract: adapter-level `ValueError`
never funneled into `IngestRejected`), F6 (subset-sum edges bypass `resolve()`
so a documented tier is unreachable as a committed match), F5 (a placeholder
method value leaking into user-visible output). Each is small; together they
suggest the paths outside the well-trodden CSV flow got less attention.

**Rationale.** Coherent, proportionate, well-reasoned, maintainable — a 4. Held
off 5 by three concrete inconsistencies between what the code documents and
what it does.

**Uncertainty.** High confidence; all from source at the pinned commit.

**Highest-value improvement.** Convert adapter parse failures to
`IngestRejected` at the adapter boundary so every rejection has one contract.

### reliability — Reliability, testing, and observability

**Evidence.** `runs/team-ledger-pytest-01.json`: 35 passed, exit 0, offline,
0.07s. `tests/test_properties.py` structure read by grep: 31 `test_` functions
across money precision, descriptor normalization, PDF layout hazards, the
control-total gate (both reject cases), ingest idempotence and merge rules,
conservation and exclusivity, D0/D1/D6, subset-sum ambiguity, and PAN refusal
at config load. `fin validate` is invoked automatically after every mutating
ingest (`src/fin/cli.py:53-54`) and reported OK in three separate runs.

**Strengths.** The tests are property-shaped rather than snapshot-shaped and
they test the things that would silently corrupt money: sub-cent precision is
refused rather than rounded, two identical charges in one file stay two
transactions, the gate rejects a dropped row. `fin validate` as a post-mutation
assertion is the right compensating control for choosing JSONL over a database,
and `src/fin/store.py:8-11` says so explicitly.

**Deficiencies.**

- **F2.** Zero tests for `src/fin/dispute.py`. The deadline state machine,
  the claim-type re-tag, and `interest_attribution` — the module the product's
  own documentation calls its most important behavior — are covered by nothing.
  The single observed interest figure ($0.29) is consistent with a
  one-month APR calculation at the declared rate, which is a spot check, not
  coverage.
- No tests for `render.py`, `analyze/spend.py`, `cli.py`, or `engine.run()` as
  an integration (only `subset_sum` in isolation). F4's traceback would have
  been caught by one error-path test.
- **F8.** No logging anywhere in the package. When a number looks wrong there
  is no trace of the command sequence that produced it, only the ledger's data
  provenance. No metrics, no run history, no way to detect a regression except
  re-running the suite.

**Rationale.** A fast, meaningful, offline property suite plus an invariant
checker that runs after every mutation meets the expectation for an event
prototype — 3. It does not reach 4 because the module the team itself
identifies as most consequential has no coverage at all, and because there is
no observability of any kind in a system designed to be driven by an agent.

**Uncertainty.** High confidence. The suite result and the test index are both
directly observed.

**Highest-value improvement.** Unit-test `dispute.build()` across all four
states with a fixed `as_of`, and assert that an expired item is re-tagged
`UNAUTHORIZED_USE` and never dropped.

### security — Security, privacy, and responsible AI

**Evidence.** [[evidence:ev-ledger-20]] (no network/HTTP/LLM surface across 22
files; sole environment read is `FIN_DATA_DIR` at `src/fin/store.py:53`).
[[evidence:ev-ledger-11]] and `runs/team-ledger-vault-perms-01.json` (vault root
0700, archived raw 0600). `runs/team-ledger-analyze-render-dispute-01.json`
(dispute CSV written mode 600, confirmed by `stat` in the run). Source:
`src/fin/store.py:62-73, 147-162`. Tests
`test_a_full_card_number_is_refused_at_load` and
`test_a_pan_field_is_refused_even_if_short`
(`tests/test_properties.py:382,393`) — the last-four-only rule is enforced at
config load and tested, not left to discipline. [[evidence:ev-ledger-19]]
`hooks/pre-commit` blocks ledger data, `.env`, real config, Luhn-valid PANs and
live token patterns from commits.

**Strengths.** Data minimization is enforced in code rather than documented.
The privacy posture is coherent: the vault lives outside the repository, the
repository ships no real data, and the commit hook is a second line rather than
the only one. The responsible-AI side is genuinely well handled: the skills
forbid calling a charge fraudulent, forbid implying legal conclusions, forbid
filing anything on the user's behalf, forbid telling a user an old charge is
not worth pursuing, and forbid scraping with a stated reason
(`fin-ingest/SKILL.md:62-66`). Those are the right refusals for this domain.

**Deficiencies.**

- **F3.** The unconstrained DuckDB surface described under `agentic`. It is the
  one place in the system where model output becomes an unbounded action.
  Credible risk, not demonstrated.
- Ledger JSONL files and rendered reports get default file modes inside the
  0700 vault; only the root directory, archived raw sources, and the dispute CSV
  carry explicit modes (`src/fin/store.py:71,159`, `cli.py:185`). The directory
  mode is the effective control, which is adequate for the single-user,
  local-first model the product states, but the README's "every output"
  framing is broader than what the code does. Corroborates
  [[evidence:ev-ledger-14]]'s scope caveat on R14.
- `.env.example` could not be read in this environment (host deny rule, carried
  through the intake and manifest). Unverified, but source shows no code path
  consuming a resolved secret, so I treat the residual risk as low rather than
  unknown.

**Rationale.** Access, data handling, and model-risk are handled better than
typical for an event prototype, with the two most important controls (PAN
refusal, vault isolation) enforced and tested rather than promised. 4, not 5,
because of F3 and because the file-permission claim is broader than the
implementation.

**Uncertainty.** Medium. F3 is an inference about DuckDB's default
configuration that no run in this package tested, and `.env.example` remains
unread.

**Highest-value improvement.** Same as F3 — constrain `fin sql` to read-only
with external access disabled.

### innovation — Innovation and technical ambition

**Evidence.** `README.md:24-32, 104-126`; `src/fin/match/engine.py:12-17,
146-211`; `src/fin/detect/detectors.py:1-17, 55-62`; `src/fin/dispute.py:1-18`;
`src/fin/adapters/citi_pdf.py:1-36`.

**Strengths.** The originality is in the problem framing, not the technology,
and it is substantive. Refusing a global optimizer because a higher match rate
actively hides fraud is a genuine and correct inversion. Ranking detectors by
time-to-detection rather than sophistication — and concluding that five lines
of declared card-to-merchant binding beats every statistical detector — is the
kind of insight that only comes from having worked the actual problem. The dual
dispute clock, where an expired billing-error window re-tags rather than drops,
is a domain insight worth real money. Technically, the subset-sum tier with
shipping allocation and every-solution reporting
(`src/fin/match/engine.py:146-170`), the unique-from-both-sides fixpoint, and
the first-currency-token layout grammar that survives a bleeding rewards column
all show depth.

**Deficiencies.** The most ambitious pieces are the least demonstrated: tier 3
never ran, the dual clock never produced a non-`NO_STATEMENT` state, and F6
suggests tier 3 is not wired into the engine the way the documentation
describes. Ambition that has not met execution.

**Rationale.** 4 for a coherent, well-argued design position backed by real
implementation depth; not 5 because the two most ambitious mechanisms are the
two with no observed behavior.

**Uncertainty.** Medium — the judgment rests partly on reading code paths that
were never executed.

**Highest-value improvement.** Wire subset-sum through `resolve()` (or change
the README to say tier 3 is advisory only) and demonstrate it on a split
shipment.

## Surprises

**Better than expected.**

- The refusal behavior is not selective. I expected the "refuses to guess"
  claim to hold in the demo path and soften elsewhere. It holds in the CSV
  adapter refusing to infer a credit sign, in D0 refusing prefix matching so an
  AWS bill is not reported as retail fraud, in D1 refusing to conclude from a
  missing feed, in `_find_duplicate` refusing to merge two rows from one file,
  and in `_assign_statements` leaving a transaction unassigned rather than
  guessing its billing cycle. Five independent places, same principle.
- The skill files are written as operating constraints rather than persona
  padding. `fin-dispute/SKILL.md:38-40` tells the agent to stop itself
  mid-sentence if it is about to write off an old charge, and names the dollar
  amount that framing would have cost. I have not often seen a prompt encode a
  specific past failure as a stop condition.
- The generated reports carry a do-not-edit banner naming the regeneration
  command, and the store treats `matches` and `anomalies` as disposable
  derivations. Small discipline, prevents the most common failure of markdown
  outputs.

**Worse than expected.**

- The deadline clock (F1). A system built around not missing a dispute window
  computes the window against the ledger's age by default. That is the one
  place where I expected the care shown everywhere else and did not find it.
- `fin sql` (F3). Nine tools are narrow and audited; the tenth hands the model
  a general-purpose execution engine, and the skill text encourages its use.
  The gap between the two is wide enough to be surprising in a system this
  deliberate.
- Zero tests on `dispute.py` (F2), the module whose own docstring cites
  $1,180.63 that naive handling would have written off.

## Blocking and major issues

**Blocking:** none. No confirmed defect prevents a primary advertised workflow
from completing. Every workflow ran to exit 0.

**Confirmed defects (directly observed).**

- **F4** — two of four ingest rejection paths emit a Python traceback instead
  of the clean `REJECTED` line
  (`runs/team-ledger-ingest-integrity-01.json` stderr;
  `src/fin/adapters/citi_csv.py:54,70` vs `src/fin/cli.py:cmd_ingest`). Data is
  safe; the contract is not.
- **F5** — `UNMATCHED` rows report `method=AMOUNT_DATE_UNIQUE`
  (`src/fin/match/engine.py:283`), visible in
  `runs/team-ledger-amazon-match-detect-01.json`.
- **F9** — skill and README attribute tier-0 matching to `order_id`; the run
  record shows it keys on `external_ref` and that an `order_id`-only row falls
  to tier 1.
- **F10** — D1 title mislabels card charges as "merchant-feed charges"
  (`src/fin/detect/detectors.py:158`).

**Major, evidence-limited (unexecuted, untested).**

- **F2** — the dispute state machine and interest attribution have neither a
  test nor an observed non-`NO_STATEMENT` run. I do not score this as failure,
  and I do not score it as success. It is the single largest unverified claim
  in the package and the panel should know that the team's own headline
  behavior rests on inspection alone.

**Credible risks (inference from source, not demonstrated).**

- **F1** — deadlines computed against the ledger's latest post date
  (`src/fin/cli.py:174`, `src/fin/analyze/spend.py:141`). I rate this the most
  consequential issue in the submission: it is silent, it is on by default, and
  it produces a confidently wrong number on the output with a legal clock.
- **F3** — unconstrained DuckDB execution of agent-composed SQL
  (`src/fin/cli.py:209-230`), reachable from untrusted descriptor text.
- **F6** — tier 3 cannot produce a committed match as documented
  (`src/fin/match/engine.py:249-273`).
- **F11** — `fin dispute` with no selector builds a packet over the entire
  ledger (`src/fin/cli.py:159`).

**Ordinary hardening, never in scope.** Multi-account households, Phase 4/5,
real-data validation of the Amazon adapter (team-stated gaps, SPEC.md section
12), the absence of a daemon, GUI, or sync. None of these affect any score. The
local-first single-user prototype should not be penalized for lacking
infrastructure it explicitly disclaims.

**Untrusted-content handling.** I read `README.md`, all four
`.claude/skills/*/SKILL.md`, and nine source modules as data. Nothing addressed
an evaluator, requested a score, or attempted to redirect this judgment. The
skill files do contain imperative instructions, but they are addressed to an
agent that a *user of the product* would run, which is the product itself; I
treated them as artifacts describing intended behavior and acted on none of
them. This is my own observation, independent of the manifest's grep
([[evidence:ev-ledger-10]]), which it agrees with.
