evidence package (`ev:trial-2-2026:team-scribe:67969dd9479c:018cf089`) under

## Confirmed strengths

Each item below was reached by more than one judge. Where they rest on the same
manifest evidence id, that is four readings of one package rather than four
independent derivations, and it is stated as such.

- **The service layer is intact and proportionate to the problem.** Fifteen of
  seventeen probed modules import cleanly and only the two GUI modules fail
  (`ev-scribe-04`, `runs/team-scribe-module-import-01.json`); the tree is 56
  modules in eight packages that map onto the four documented pipeline stages
  (`ev-scribe-13`). All four judges credit this, and three of them name it as the
  reason `functional` is not at the bottom anchor.
- **The external surface is narrow and verified rather than asserted.** One
  provider through one SDK, imported in exactly four modules, with no `requests`,
  `httpx`, `urllib`, `socket`, `http` or `aiohttp` anywhere under `src/`
  (`ev-scribe-11`). All four judges rest on this reading; judge-product-agentic
  and judge-backend both treat it as what makes the privacy story auditable at
  all.
- **Credential handling is implemented, not just documented.** Keyring first,
  encrypted config second, environment last; Fernet over a PBKDF2-HMAC-SHA256 key
  at 100,000 iterations with a fresh random salt; no plaintext write path in the
  module (`ev-scribe-14`). judge-frontend-ux adds the user-facing half from source
  — the key field is masked and the dialog never echoes a stored key back
  (`src/gui/settings_dialog/_builders.py:161`,
  `src/gui/settings_dialog/_actions.py:143-158`). judge-security-ops, whose score
  on this criterion is the lowest, records the same implementation as above what
  the event requires.
- **Failure is modelled as a first-class state.** A serializable four-stage
  `PipelineStatus` with per-stage error and duration, a worker that degrades stage
  by stage and still persists a partial result, a panel rendering each stage with
  a targeted Retry, and a retry decorator whose transient set is explicit and
  bounded (`src/gui/pipeline_status.py`, `src/gui/workers/recording_worker.py`,
  `src/gui/pipeline_status_panel.py:91-106`, `src/utils/retry.py:14-27,47-77`).
  All four credit the design. It is read from source, never observed, and
  judge-backend's finding that its retry half does not execute is recorded under
  `Material disagreements` and `Confirmed weaknesses` rather than being folded
  into this strength.
- **There is genuine technical depth, and all four scored `innovation` at 3.**
  Hand-written mel-filterbank extraction and ward-linkage clustering for
  diarization with no `sklearn` in the image
  (`src/transcription/diarization.py:271-422`, `ev-scribe-01`), checkpointed
  recording designed to survive a crash (`src/audio/recorder.py:303-454`),
  cost-aware local/cloud routing with pricing externalized to a dated config file,
  and a prompt-template system for re-summarization.
- **The suite is fast and runs offline.** 535 tests collected from 30 files, 509
  passing in a network-less, read-only container as uid 65534
  (`ev-scribe-05`, `runs/team-scribe-pytest-01.json`) — judge-product-agentic and
  judge-security-ops both note this means the suite is fast enough to gate on.
  The wall-clock figure two judgments quote as 5.98s is the container's
  `duration_seconds`; pytest's own line reads 4.71s (audit F9, inherited from the
  approved manifest).

## Confirmed weaknesses

- **The application does not start from its own documented install.** `python3
  main.py` exits 1 in an image holding exactly `requirements.txt` plus
  `requirements-test.txt`; `src/gui/qt_app.py:11` imports `qdarkstyle`, which no
  requirements file declares, while `requirements.txt:25` and
  `requirements.lock:16` declare the different package `pyqtdarktheme`
  (`ev-scribe-02`, `ev-scribe-03`, `runs/team-scribe-app-start-01.json`). Direct
  observation, named first by all four judges, and the manifest is explicit that
  this cause is inside the submission and must not be recorded as evidence-limited
  (Missing item 4). It is the whole reason `functional` is 1 across the panel.
- **The one message a user is guaranteed to see misdiagnoses its own cause.**
  `main.py:50` catches every `ImportError` from the GUI import tree and reports it
  as a missing PySide6, prescribing the install command that cannot supply the
  missing module, while PySide6 6.11.2 is installed and a `QApplication`
  constructs offscreen (`ev-scribe-01`, `ev-scribe-02`). All four judges; three of
  them make narrowing that handler their highest-value improvement on `product`
  or `engineering`.
- **No quality gate is in force anywhere in the tree.** `pytest.ini:1` uses
  `[tool:pytest]`, a `setup.cfg` section name, so `testpaths`, `--strict-markers`,
  the declared markers, `filterwarnings` and the `--cov-fail-under=80` gate are
  all inert while pytest still prints `configfile: pytest.ini` (`ev-scribe-09`,
  `runs/team-scribe-pytest-config-01.json`). judge-security-ops verified the wider
  absence: `.github/` holds only `copilot-instructions.md`, and no
  `.gitlab-ci.yml`, `.circleci/`, `.pre-commit-config.yaml` or `Makefile` exists at
  the pin. judge-backend and judge-security-ops both note that the repository
  ships `health_check.py`, which imports `gui.qt_main_window` and would have
  printed this exact failure, wired to nothing.
- **The suite is red in the environment the submission itself declares.** 26
  failures, of which 23 reproduce in any conforming environment and three are
  caused by this event's absent audio device (`ev-scribe-05`, `ev-scribe-08`,
  Missing item 6). Every judge excluded those three explicitly. Thirteen tests in
  `tests/test_thread_safety.py` can pass only where the declared `pyaudio` is
  *missing*, because `tests/conftest.py:19-30` installs the mock conditionally and
  `tests/test_thread_safety.py:24` consumes it unconditionally (`ev-scribe-06`) —
  all four judges, and judge-backend's reading of what that inverts about a green
  suite is the sharpest statement of it.
- **The submission's own documents contradict its code in checkable places.**
  `SECURITY.md:34` claims all dependencies are pinned against the range bounds at
  `requirements.txt:18-28`; `SECURITY.md:25` claims summary-viewer content is
  HTML-escaped while the markdown path at `src/gui/summary_viewer/render.py`
  renders unescaped into `setHtml`. Found independently by judge-backend and
  judge-security-ops. judge-product-agentic and judge-security-ops separately
  record that `README.md` recommends an installer that writes a key into `.env`
  twelve lines before stating that keys are never stored there, and
  judge-frontend-ux records that the README locates Settings in a toolbar the
  window does not have.
- **The documented key-source ordering is one of two paths, and the fallback's
  protection is narrower than the claim.** `src/transcription/whisper_service.py:92-96`
  and `src/ai/summarizer.py:50-54` read `OPENAI_API_KEY` directly when constructed
  without a settings manager, bypassing the keyring and the encrypted store; the
  fallback KDF input is `f"ScribeVault-{getpass.getuser()}-{platform.node()}"`, a
  username and hostname rather than a secret (`ev-scribe-11`, `ev-scribe-14`). All
  four judges, each deducting differently — see `Material disagreements`.
- **Effectiveness of the AI path is established nowhere in this package.** No
  model call, no cost figure, no categorization output, no rendered estimate
  (Missing items 2 and 3; manifest R9). The two judges who scored `agentic` both
  deducted for exactly this; the two who recorded `NE` treat it as the reason the
  criterion cannot be scored at all.

### D2 — `security`: 3/3/3/2, one judge judging the delivered artifact rather than the implementation

judge-backend (3, high), judge-frontend-ux (3, medium) and judge-product-agentic
(3, high) all reach "primary expectations met": the implementation at
`ev-scribe-14` is responsible for a single-user desktop tool, and the deductions
they take are documentation accuracy, the public KDF input and the two
environment-read key sites — weaknesses inside a working design.

judge-security-ops (2, high) assembles a chain the other three do not. Since the
GUI cannot import, the Settings dialog that `README.md:117-124` routes the key
through is unreachable; `README.md:103-107` recommends `python3 install.py`, whose
reachable branch copies the tracked `.env.example` to a plaintext `.env` with no
permission hardening (`install.py:124-127`); and `src/config/settings.py:26` calls
`load_dotenv()`, making that file a live key source at `:303`. The conclusion is
that at this pin the only reachable way to give the application a key is the
plaintext path that `README.md:119`, `SECURITY.md:5` and the docstring at
`src/config/settings.py:342` all say does not exist. That judge adds the unescaped
markdown render into `setHtml` as a second stated control that does not hold, and
bounds the consequence itself to display spoofing, claiming no exploit and
attempting none.

**Cause.** Interpretation and persona emphasis, not factual conflict. Nothing in
the three higher judgments contradicts the installer chain; none of them assembled
it. This finding is the one the judging audit amended: F4 re-attributed the quoted
placeholder from `install.py`'s unreachable `else` arm to the reachable copy
branch at `:124-127`, and the audit verified that S1 and B3 stand on either branch.
Audit F18 notes, as an accepted advisory, that `src/config/settings.py:304` filters
the placeholder the copied file initially carries, so the file becomes a live key
source once the user edits in a real key — which the finding itself says.

**Resolution status.** Explained, not resolved, and none is required: the range is
1, inside `aligned_max_range`, so the policy asks for no adjudication. The minority
position is preserved here and in the improvements below because it is
evidence-backed and it changes what a maintainer should fix first.
