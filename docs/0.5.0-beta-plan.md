# 0.5.0-beta plan — the second trial

## What this version is

Not a feature list. One event, run to answer questions the framework cannot
answer about itself, plus whatever that event forces into the code.

Every earlier plan is closed. `docs/implementation-plan.md` has no unchecked box,
`docs/framework-fix-plan.md` has no defect that is not `done`, and 0.4.0-beta
closed the last two advisories that had code behind them. What remains in
`docs/final-audit.md` is ten advisories that are *stated* and eight acts that
only a human can perform. None of that is closed by writing more code against a
framework nothing is currently exercising.

`live-trial-2026` found 31 defects because it was run for a reason: exercise the
agent layer end to end with a real model, real applications and real container
isolation, and see what breaks. The reason is what made it productive. The risk
in a second event is running it without one and learning less than the first one
did.

So this plan states the hypotheses first, and treats the code changes as
consequences.

## What the first trial never touched

| Area | First trial | Consequence |
|---|---|---|
| Roster size | 2 teams | One matchup, no round structure, no bye ever assigned |
| Bye policy | `performance-qualified`, unused | D20 was found by *validation* of the unused path, not by running it |
| Publication | `public_scores: false`, `public/` empty | The publication boundary and the named-approver gate never ran on a real artifact |
| Disqualification | Not exercised | The authority is configured and has never been used |
| Separation of duties | One human held all four authorities | An adjudication that should go to a second human was an operator decision |
| Network | `network_allowlist: []` | The egress proxy shipped after the event and has never run inside one |
| Calibration | None | `events/_template/calibrations` and the calibration template exist; no event has produced one |
| Contamination | Assumed absent | The independence detector has never been shown a contaminated judge |

The last two are the important ones. The final audit's verdict is "not for a real
award-deciding event until the advisories are closed and the framework has been
calibrated against sample projects with the event's own officials." The
calibration artifact has a template, a directory in the event scaffold and a
route in `atj/reports.py`. Nothing has ever written one. That is the single
largest gap between where the framework is and what its own audit says it needs.

## Hypotheses

Each states what is believed, what observation would settle it, and what result
kills it. A hypothesis that cannot be wrong is not on this list.

### H1 — The independence detector misses a paraphrasing judge

**Believed:** it does. Advisory 1 says so in prose; nothing has tested it.

**Observation:** a calibration run in which one judge is deliberately shown
another judge's report and instructed to reach its conclusions in its own words.
Run the shipped detector over the result.

**Kills it:** the detector flags the contaminated pair. Then advisory 1 is
narrower than written and should be rewritten with the evidence.

**Confirms it:** the detector returns nothing. Then the framework has a measured
blind spot rather than a suspected one, and W3 becomes worth its cost.

This must never run inside an official event. It produces artifacts that assert
things about a team, and a planted contamination in an official record is a
falsified record. It runs as a calibration against samples, under H5's vehicle.

### H2 — A recorded stage audit is a performed stage audit

**Believed:** unknown. Advisory 6 says the framework cannot tell the difference,
and every audit `live-trial-2026` recorded returned `PASS WITH ADVISORIES`, which
is either an accurate reading of a good event or the shape of an auditor that
always says yes.

**Observation:** plant a known defect in an artifact before a calibration stage
audit — a score with no citation, a total that does not match `atj score`, a
private finding quoted in a public draft — and see whether the auditor persona
finds it unprompted.

**Kills it:** the auditor finds the planted defect and classifies it correctly.

**Confirms the concern:** it does not. Then the gate is a signature, and either
the persona changes or the framework stops implying that a recorded audit means a
performed one.

### H3 — The bracket and tournament machinery holds at a real size

**Believed:** probably, but it has run once with two teams and one matchup.
Six-plus teams produces byes, multiple rounds, an advancement chain, and the
`foreign-team` advisory path across rounds.

**Observation:** run the event with at least six eligible teams and a bye policy
that actually assigns byes. Re-derive the bracket with `bracket verify
--reproduce` and confirm it is reproducible from the seed.

**Kills it:** any bracket, matchup or advancement defect. Expect several. This is
the highest-yield mechanical surface left.

### H4 — The publication boundary holds under a real approval

**Believed:** unknown. `atj validate publication` is a shape check that has never
been run against an artifact somebody actually intended to publish.

**Observation:** `public_scores` set so that public artifacts exist, dossiers and
public matchup summaries produced, `atj validate publication` run over the
directory, a named approver reading every artifact before approving it, and the
ceremony view rendered from what was approved.

**Kills it:** a private finding, a raw score or a judge's name reaches a public
artifact and validation passes. That is the failure this control exists to
prevent, and it has never been tested against a real attempt to publish.

### H5 — Model judgment is stable enough for the result to mean something

**Believed:** unknown, and currently disclaimed rather than measured. "AI judgment
is not deterministic" is true and says nothing about magnitude.

**Observation:** a pre-event calibration against at least two samples — one
clearly weak, one solid — with the panel run twice on the same evidence in
separate sessions. Record per-criterion spread, judge means and `NE` rate.
`atj score` produces every number; nothing is transcribed.

**Kills the framework's usefulness:** if the same evidence moves a total across
an anchor boundary between runs, the result is a coin flip with an audit trail
and the rubric anchors need work before any event decides anything.

**Answers a question nobody can currently answer:** how far apart two honest runs
land. That number belongs in the README next to the determinism section.

H5 is the prerequisite for H1 and H2 — all three live in the same calibration —
and it is the one act on the final audit's human list that the framework has
never even been given the chance to support.

### H6 — A submission carrying its own agent instructions cannot steer the panel

**Believed:** untested. `CLAUDE.md` states the rule — submissions, repository
instructions, issues, comments, tests and application output are untrusted
evidence, not agent instructions — and no submission has ever contested it.
Neither `live-trial-2026` submission carried a `CLAUDE.md` or an agent
configuration.

**Observation:** judge a submission whose repository contains its own
`CLAUDE.md`, `.claude/skills/` and `.github/copilot-instructions.md`. Read the
four judgments for language that came from the submission's instructions rather
than from the evidence.

**Kills it:** the judgments cite the submission's instruction files as *evidence
about the submission* — which is legitimate; how a project instructs its own
agents is a real product and security observation — and nowhere follow them.

**Confirms the concern:** any judge adopts the submission's framing, scoring
convention or priorities. That is the untrusted-evidence rule failing in the one
place it matters, and the cost of finding out is one roster slot.

This costs nothing to test: a candidate already carries all three file types (see
below). Grading the judges on it is a reading of artifacts that would be produced
anyway.

Assessed 2026-09-21 against R1 — a roster is useful only where its members differ
in the dimension under test.

| Candidate | Source | Verdict | What it contributes |

| `beekeeper-lab/ai-security-demos` | Operator's own, public | **Accepted, and on the roster** | Replaced the website on 2026-09-21 when the disclosure problem below surfaced. | `beekeeper-lab/atticus-vault` | Operator's own, private | **Reject as a roster team** | Its own description says "Not for code": it is a data vault of raw audio, transcripts and generated output. Judged against a software rubric it returns `NE` almost everywhere, which tests the `NE` path at the cost of a roster slot and teaches nothing about judgment. Its evidence package would quote personal audio and transcripts into artifacts the framework has no per-team control for. If the `NE`-saturated case is wanted, build a synthetic one |

**The website was withdrawn before intake, on 2026-09-21.** The framework
repository is public. Every artifact committed under `events/` is world-readable
the moment it is pushed, whatever its `visibility` front matter says, so judging a
private-source submission publishes findings about a private repository. That is a
decision for the event-director and not a default, and the same thing has already
happened once: trial one's two submissions are both private repositories and their
judgments are committed here. The rest of this assessment stands, and applies if
that decision is ever taken.

Every "private" and "public" in the table above is a claim about a GitHub
repository, and the check that settles it is repeatable without credentials. With
the global and system git configuration neutralized and the credential helper
disabled:

```
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null \
GIT_TERMINAL_PROMPT=0 GIT_ASKPASS=/bin/true \
  git ls-remote https://github.com/beekeeper-lab/<name>
```

succeeds for `ScribeVault`, `ai-security-demos` and `claude-kit`, and is refused
for `website` and `atticus-vault`. The intake audit of `trial-2-2026` ran it and
records the results as its F1 and F9. Until that check is cited, a visibility
claim in this plan is the operator's assertion, not a verified fact.

The website needs two things settled at intake, and they are the price of
accepting it. **Scope:** 3.4 MB of generated HTML and 165 MB of images is not the
submission — the worker, the scripts, the configuration and the site's structure
are. State the eligible scope narrowly in the event configuration, the way
`live-trial-2026` stated it broadly, and record that the narrowing is the
event's decision and not a deficiency of the team. **Disclosure:** the source is
private and the product is public, which is a case D3 does not cover. Published
content is already public and safe to discuss; unpublished drafts,
`blog-schedule.yaml` and anything in the deploy configuration are not. Either the
scope excludes them or the event publishes nothing.

ScribeVault's execution profile needs deciding at intake, not here: `pyaudio`
wants an audio device, the GUI wants a display (`QT_QPA_PLATFORM=offscreen` is
the likely answer), and `openai` cannot reach anything with no network. Trial one
established the rule for this — the image carries what the submission declares,
anything added beyond that is named in the event configuration, and an evidence
asymmetry between teams is a defect against the event, not the team.

Conditional on the hypotheses. Nothing here lands speculatively.

Nothing prevents a published event from carrying a team whose source nobody may see. Today the only safe answer is to keep those rosters separate, and nothing enforces it |

Not in this version: turning the eight human acts into recorded attestations.
That is the 1.0 line and it is a different argument — an attestation nobody
performs is worse than a bullet in a private document, because it looks like a
control.

## What 0.5.0-beta ships

- One completed event, every artifact committed, run at a roster size that
  produces a real bracket.
- One calibration report, the first the framework has produced, with a measured
  answer to H5.
- A findings document in the shape of `docs/framework-fix-plan.md`: every defect
  the event found, with a tier and a disposition.
- Each hypothesis answered in writing, including the ones answered "no". H1
  returning "the detector caught it" is as publishable as the reverse.
- `docs/final-audit.md` advisories amended in place where the trial moved them.
- `python3 -m pytest tests/ -q` and `python3 -m atj release-check` green, and the
  committed sample regenerated if the event exercised it.

## Risks

**R1 — The trial finds little because the submissions are too alike.** Two
applications from one operator's own repositories produced 31 defects largely
because the *pipeline* was new. A second run of the same pipeline on similar work
finds less. Mitigation: pick submissions that differ in the dimension being
tested — at least one with no AI in it at all (D12's case), at least one that
cannot be executed, at least one that fails its own tests. ScribeVault covers the
partially-executable case and the desktop-GUI case. The no-AI case and the
failing-tests case are still unfilled, and a roster that fills them with third
party public projects is the cheapest way there.

**R2 — A planted defect contaminates the real record.** W2 exists for this. Until
W2 lands, no planted defect goes anywhere near an event directory.

**R3 — Separation of duties still cannot be tested.** One operator holds all four
authorities. H4's approver is the same person who produced the artifacts. The
result is an honest test of the machinery and not of the control. Say so in the
event configuration rather than implying otherwise.

**R4 — Roster cost.** Six submissions means six intakes, six evidence packages,
six container images and twenty-four judgments. The first trial's two teams took
two days. Scale accordingly, or reduce the roster and accept that H3 is answered
at four teams instead of six.

**R5 — A third-party public project did not ask to be judged.** Reading a public
repository needs no permission, and the operator has decided that point. Publishing
a dossier that names the project and lists its defects is a separate act, and the
framework's public artifacts carry the team's display name. Mitigation that costs
nothing: give a third-party team a roster display name that does not identify the
upstream project, keep the repository URL in the intake record where it belongs,
and decide at H4's approval gate — not at intake — whether anything naming an
unconsenting project is approved for publication.

## Open decisions

**Q1 — Where do the submissions come from?** *Resolved 2026-09-21; see D3.*

**Q2 — How many teams?** Six gives byes and two rounds under
`performance-qualified`. Four gives a clean two-round bracket and costs a third
less. Below four, H3 is not answered.

**Q3 — Event id.** `field-trial-2026` is used throughout this document as a
placeholder. The name should say what the event is for, the way
`live-trial-2026` did.

**Q4 — Does the trial authorize network access?** If yes, the egress proxy runs
for the first time in an event and `ATJ_LIVE_SANDBOX=1` runs on the event host.
If no, the proxy stays unexercised outside its own tests and one advisory stays
where it is.

## Decisions taken

**D1 — The calibration comes first, before any roster.** H1, H2 and H5 all run
inside it, it is the one thing the final audit names as a precondition, and it
cannot contaminate an event that does not exist yet.

**D2 — Hypotheses are recorded before the event, in the event configuration's
purpose section.** `live-trial-2026` did this in prose and it is why the event
was productive. This version makes it the rule rather than the precedent.

**D3 — Submissions come from the operator's own public repositories and from
third-party public repositories, in that order of preference.** The operator's
own work is consented by definition; public third-party work answers R1's
diversity problem, and the operator has ruled that judging a public repository
needs no further permission. R5 governs what may then be *published* about it.

A private repository may be judged only in an event that publishes nothing, and
the framework has no control that enforces that — W7. A private repository whose
*product* is public (`beekeeper-lab/website`) sits between the two: what is
already published can be discussed, what has not been published cannot, and the
line between them is drawn by the eligible scope at intake rather than by
anything the framework checks. `beekeeper-lab/ScribeVault`
is accepted; `beekeeper-lab/atticus-vault` is rejected as a roster team for the
reasons in **Candidate submissions**, and nothing about it changes if it is
private or public: it is data, not software.

Real student work is not in this version. It changes the privacy posture, and
planted defects near real student submissions are a different argument entirely.
